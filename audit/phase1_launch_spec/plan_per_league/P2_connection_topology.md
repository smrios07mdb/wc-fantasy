## 2. The math (the D-DB-brief artifact)

**Model.** Total client connections into a given Supavisor =
`Σ over services s of  instances(s) × K(s) × L(s)` where **K(s)** = distinct PrismaClients per instance (R-1: up to N leagues cached; R-2: 1) and **L(s)** = explicit `connection_limit` (mandatory per §3; defaults are cpu-derived and unbudgeted).
Reference sizing used in the table: L_web=5, L_worker=5, L_cron=2 ⇒ resident per-league client budget **R = I_w·L_w + L_k = 10** (+4 transient at cron overlap). Server side: Supavisor opens ≤ **P** conns to Postgres **per (user,database) pool**. Server budget = **0.8·X − S**, where **S** = Supabase platform services (Auth/GoTrue, PostgREST, Realtime, storage) + `reserved_connections`, which consume DIRECT connections against the same X (VERIFY S on the dashboard at decision time; on Micro the effective user budget is nearer ~40 than 48 — this only tightens the V-c / role-per-league conclusions below).

⚠️ **Correlated peak**: every league is the SAME World Cup — kickoffs are synchronized, so N leagues' traffic peaks land at the same instant. Per-league sharding buys zero temporal load spreading; size everything for simultaneous peak.

## 3. F-A07 resolution under per-league (the pin)

Under EVERY per-league variant, F-A07's fix stops being optional hygiene and becomes structural: the DSN count goes from 1 to N, so a manual runbook step (RUNBOOK.md:22,65) cannot scale — **`pgbouncer=true` + explicit `connection_limit` + `pool_timeout` must be asserted/appended IN CODE at a client factory**, and packages/db/src/index.ts:12-16's module singleton must be replaced:

- **Factory (all variants):** `makePrismaClient(dsn, {connectionLimit, poolTimeout})` in @app/db that parses the DSN, asserts port 6543 ⇒ requires `pgbouncer=true`, and appends `connection_limit=L&pool_timeout=10`. R-2: singleton = `makePrismaClient(env.DATABASE_URL)` — the 93 `@app/db` importers are untouched. R-1: a keyed registry `Map<leagueId, PrismaClient>` (LRU-capped, §SUB-3) — the 93 import sites can no longer import a bare `prisma`; that rewrite is the session→DB routing lane's scope, but the registry/factory shape is fixed here.
- **DSN shapes:**
  - **V-a:** per league ℓ: `postgresql://postgres.<ref_ℓ>:<pw_ℓ>@aws-0-<region>.pooler.supabase.com:6543/postgres?pgbouncer=true&connection_limit=L&pool_timeout=10` (host shape per RUNBOOK.md:89) + per-league `DIRECT_URL` (:5432) for migrate. N secret pairs.
  - **V-b:** one host: `...:6543/postgres?schema=league_<ℓ>&pgbouncer=true&connection_limit=L&pool_timeout=10`. **Transaction-mode honesty:** Prisma applies the `schema` param by qualifying generated SQL (believed — `"schema"."table"` in emitted queries), NOT by session `search_path`, which would be unsafe under transaction pooling (server conns are shared across clients between transactions). **W0-class SPIKE required before V-b is admissible**: confirm on the lockfile-resolved Prisma version (6.19.3 today — re-read pnpm-lock.yaml at spike time, not the `^6.2.1` manifest floor) that every generated query is schema-qualified under `?schema=` + `pgbouncer=true`. Repo raw-SQL audit: the two `SET LOCAL app.commish_override` sites (packages/lineup/src/prismaStore.ts:94, packages/faab/src/prismaStore.ts:790) are inside `$transaction` ⇒ transaction-pooler-safe (interactive txn pins one conn; SET LOCAL is txn-scoped); remaining raw sites (db-check route.ts:21 `SELECT 1`, backfill runner) carry no schema-relative table refs — but ANY future `$queryRaw` naming a table unqualified silently resolves to `search_path`=public ⇒ lint-fence needed.
  - **V-c:** `.../league_<ℓ>?pgbouncer=true&...` (database name varies) — moot if §2's math + P1 hold.
- **Migrations stay off the transaction pooler** (render.yaml:53-55, schema.prisma:30 — already correct) but multiply: **×N `prisma migrate deploy` runs** against N direct URLs (V-a) / N schema params (V-b). `preDeployCommand` runs once per web deploy ⇒ R-1 needs a loop-over-targets migrate script with per-target failure isolation. **NEW failure class on top of F-A15's forward-only-no-down**: a mid-loop failure leaves league k migrated and league k+1 not — partial-fleet schema skew *within one deploy*, on top of the already-absent cross-service ordering barrier (Lane A3: only web migrates, all 4 services deploy independently).
- **One-DB contrast (3-4 lines):** the identical code-level fix (factory asserting `pgbouncer=true` + explicit `connection_limit`) is needed under one-DB too — F-A07 is fork-independent. Difference: one-DB keeps K=1 client per process and 1 DSN pair, so the fix is the S-effort audit item with no registry, no ×N migrate loop, no budget model. Per-league converts F-A07 from a hygiene item into this lane's entire §2 budget discipline.

## 4. Worker/cron topology

**Load-bearing fact:** feed data (fixtures/stats/rosters) is league-independent reference data (player/fifa_team come only from ingest; prod 1252/48 — apps/worker/package.json:17 `job:rosters` → src/jobs/syncRosters.ts; ARCHITECTURE.md:168). Under per-league DBs each DB holds its own COPY, so "×N ingest" splits into fetch and write halves:

- **R-1 (one worker, N DB targets):** keep ONE fetch (one process, one in-process limiter ⇒ **F-A20 stays satisfied**), then fan out writes serially: fetch-once-fan-out-writes. Tick budget: the 60 s scheduler tick (ARCHITECTURE §3; re-entrancy guard scheduler.ts:68,72) now runs t_fetch + N·t_write; overlapping ticks are skipped, not queued ⇒ staleness grows linearly with N. Client shape per §SUB-3: cached N clients (N·L_k against poolers — counts in §2's R) vs per-league ephemeral connect/disconnect (Supavisor absorbs client churn cheaply — that is its purpose — but Prisma engine spawn per league per tick is CPU-costly in-process).
- **R-2 (worker-per-league, ×N):** N resident workers each fetch the SAME global feed with ONE `BALLDONTLIE_API_KEY` and the per-process in-memory limiter (packages/feed/src/rateLimiter.ts:17-28) that has **no 429 backoff** (client.ts:69 throws, scheduler catches and retries next tick) ⇒ aggregate rate = N × configured RPM, uncoordinated — **this is F-A20's exact "do not scale >1 process" constraint violated by construction, and a NEW CONSTRAINT for the D-DB flag list**. Mitigations: (a) divide `BALLDONTLIE_RPM` (env-configurable, render.yaml:107,207) by N ⇒ freshness degrades linearly; (b) distributed limiter + 429 backoff (F-A20's fix, now mandatory not optional); (c) **hybrid axis**: R-2 web (no routing problem) + ONE R-1 multi-DB ingest worker (F-A20-safe) — the axis can be chosen per service class (§SUB-1).
- **Crons ×N:** R-1 = one cron looping N targets sequentially (hourly period-close binds only when N·t_league approaches 1 h — not a realistic bound); R-2 = N cron pairs (2N Render crons, pure cost/ops).

## SUB-DECISIONS (for the D-DB brief)

1. **SUB-DECISION: deployment axis per service class — uniform R-1, uniform R-2, or hybrid (R-2 web + single R-1 ingest worker + R-1 crons)?** — A: uniform R-1 (one fleet, needs client registry + routing, F-A20-safe); B: uniform R-2 (no routing, 4N services, F-A20 breach needs (a)/(b) above); C: hybrid (kills both the routing-in-web problem and the F-A20 breach; cost = one bespoke multi-target worker).
2. **SUB-DECISION (V-b only): shared DB role vs role-per-league** — A: shared role = ONE (user,db) pool, per-league server slots ≈ P/N, noisy-neighbor at correlated peak; B: role-per-league = pool isolation via (user,db) keying but Σ N·P_ℓ ≤ 0.8·X − S caps hard (P_ℓ=2 at N=20, Micro; S = platform services + reserved_connections, VERIFY on dashboard). Depends on the §1 keying VERIFY.
3. **SUB-DECISION (R-1 only): client registry policy** — A: unbounded Map (RAM binds ~N≈20-30 on starter, §2); B: LRU-capped K clients with connect-on-demand (bounded RAM, reconnect latency on eviction); C: per-request ephemeral (no cache; engine-spawn CPU per request — likely untenable for web, tenable for crons).
4. **SUB-DECISION: connection_limit sizing (L_w/L_k/L_c)** — must be chosen jointly with instance plan: `Σ inst·K·L ≤ M` and `≤ 0.8·X − S` server-side; A: small fixed L (5/5/2, table above); B: C_default(cpu) formalized — rejected implicitly by F-A07 (unbudgeted, cpu-dependent).
