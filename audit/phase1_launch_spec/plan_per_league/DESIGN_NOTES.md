# Per-league-DB fork — DESIGN NOTES (synthesis of lanes P1–P5)

_Per-league-DB spec pass, 2026-07-06. Synthesis: Fable 5 (orchestrator). Sources: P1–P5 lane files in this directory (each independently verified, verdicts folded in place), consuming the phase-1 inventories (L1/L2/L4), `audit/AUDIT_LAUNCH_readiness.md`, `render.yaml`, and the parent one-DB spec `../DESIGN_NOTES.md`. Companion to the one-DB fork spec: together they make **D-DB** (`../DEC0_DEPENDENCY_MAP.md` row 1) decidable. **This pass picks no fork** — it completes the spec pair; the decision is Sergio's/DEC-0's._

## 0. Executive summary

1. **The taxonomy has three per-league hosting variants; one is dead.** **V-a** project-per-league (own Postgres/Auth/Realtime/keys per league) is Supabase's recommended shape and fully viable. **V-b** schema-per-league (one project, `?schema=` per league) is viable *only after* paying repo-specific landmines (§P1) and passing an unrun pooler spike. **V-c** (extra `CREATE DATABASE` in one project) is **dismissed with evidence**: dashboard-invisible, unusable with PostgREST/Auth/Storage/Realtime (P1 §1), and independently dead on connection math (X binds at N≈2–3, P2 §2). Orthogonally, the deployment axis — **R-1** shared app fleet routing N targets vs **R-2** service-set-per-league — can be chosen **per service class** (P2 SUB-1: e.g. R-2 web + one R-1 multi-target ingest worker).
2. **The headline that motivated this fork survives, with a caveat.** Under per-league, `fifa_match.periodId` stays a single-column FK and the **entire L4 junction apparatus evaporates** — the `match_period` table, composite FK, E1–E6 expand/contract ladder (incl. the destructive E6 point of no return), waves W0–W5, the raw-SQL trigger rewrite, and the CI fence (P5 §1). All 56 L1 consumer sites: 50 correct-by-construction; **5–6 become load-bearing-by-topology** (the ingest `resolvePeriodId` cluster, the module-memoized nav phase under R-1, M8) — correct today, but defended by nothing once L4's fence is deleted (P5 §2, flag F-3).
3. **"No migration at all" is V-a-only and KEEP-VESTIGIAL-only.** V-b requires rewriting/templating the migration history (37 `public.`-qualified occurrences across 8 of 30 migration files land in `public` regardless of `?schema=`) plus an `auth.users`→N-schemas mirror-trigger fork (P1 §1, P3 S3). And DROPping the now-vestigial `league_id` apparatus (13 models) is ×N cleanup migrations — the zero-migration reading requires keeping the multi-tenant schema shape as dead weight (P5 §3, SUB-DECISION).
4. **RLS does not collapse — anywhere.** 0 of 27 policies and 0 of 4 SECDEF/trigger helpers EVAPORATE under either variant. 17/27 are OWN-class *intra-league* isolation (blind FAAB bids, hidden pool picks, private push/watchlist rows) that per-league hosting cannot address. Under V-a, 8 LM policies may *optionally* simplify (zero-diff is the reversible stance); under V-b the LM predicates are **promoted to the sole cross-league read barrier** and the surface *grows* machinery (per-schema replication, search_path re-pins, PostgREST grants) — **V-b is strictly more RLS/authz work than one shared DB** (P3 §2).
5. **Connections: V-a never binds server-side; V-b binds early.** Per-league × per-service pool math (P2 §2): V-a's multiplication lands client-side (R-1: N cached PrismaClients per instance → RAM binds ~N≈20–30 on starter) or on cost (R-2 = today ×N). V-b shares one Supavisor pool with **perfectly correlated peaks** (every league is the same World Cup): `pool_timeout` storms from ~N≈3–5 (deferrable ~2–3× by raising P), `max_client_conn` binds at N≈20 (halves if web scales to 3 instances). **F-A07's fix (code-level `pgbouncer=true` + `connection_limit`) is mandatory pre-work under every variant — and under one-DB too; per-league just multiplies the DSNs it must govern.**
6. **The biggest V-a constraint is auth fragmentation, not data.** Per-project Auth means a multi-league human = N unlinked `auth.users` rows, N magic-link sign-ins, no SSO; per-project Auth config (Site URL, redirect allowlist, SMTP) is a ×N birth step; and `NEXT_PUBLIC_SUPABASE_URL/ANON_KEY` are **build-time-inlined** (render.yaml:64-66), so one shared R-1 build cannot carry N projects' browser keys — **V-a couples strongly to R-2** absent a runtime-config refactor (P3 §4, P4 §2).
7. **R-2 is the zero-code-change pole with a hidden breach.** Today's code (singleton client, 7 `league.findFirst` call sites, build-time keys) runs byte-unchanged per league — but N workers each pulling the feed with one API key and N uncoordinated in-process limiters **violates F-A20 by construction** (P2 §4, P4 §5). The fetch-once-fan-out-writes R-1 worker (or the hybrid) is the F-A20-safe shape.

## 3. NEW-CONSTRAINT FLAGS — what the one-DB DESIGN_NOTES missed or understated

The parent exec summary priced per-league as "×N ingest, ×N migrations, no cross-league surfaces, and a new session→DB routing problem" (`../DESIGN_NOTES.md` §1 pt 2). This pass found that framing incomplete:

| # | Flag | Source |
|---|---|---|
| F-1 | **Expand/contract becomes mandatory and permanent.** Any ×N migration loop can partially fail ⇒ mixed-schema fleet with one code version serving both — a failure class F-A15's forward-only discipline doesn't cover. Under per-league there is never a deploy where "the" database is atomically at one version. | P1 §4, P2 §3 |
| F-2 | **V-b is not migration-free and not yet admissible.** 37 `public.`-qualified raw-SQL occurrences (8/30 migration files) defeat `?schema=`; the mirror trigger needs a fan-out fork; and whether Prisma schema-qualifies every generated query under `?schema=` + transaction pooling is **unverified on the lockfile-resolved 6.19.3** (W0-class spike; prisma#28611 shows the mechanism regressing on the v7 adapter path). | P1 §1 + V-P1 finding 6, P2 §3 |
| F-3 | **The junction's deletion also deletes its defense.** One-DB actively guards period↔league consistency (composite FK + CI fence); per-league replaces that with an *undefended topology invariant*. The vestigial `[leagueId,…]` uniques do NOT protect the highest-risk site: a mis-inserted second league would let `resolvePeriodId` (`findFirst{kind,label}`, no league filter) stamp the wrong league's period silently. If per-league is chosen, a cheap guard (e.g. a `league`-table single-row CHECK/trigger or startup assertion) should be specced in. | P5 §2/§3 + V-P5 finding 1 (CONFIRMED design hole) |
| F-4 | **V-a×R-1 build-time key seam.** `NEXT_PUBLIC_SUPABASE_URL/ANON_KEY` are inlined at `next build`; one shared build cannot serve N projects' browser Auth/Realtime. V-a effectively forces R-2 or a runtime-config refactor of the Supabase client layer. | P4 §2, P1 §2 B7 |
| F-5 | **"×N ingest" is a correctness breach under R-2, not just N× work.** N workers = N uncoordinated in-process rate limiters on one vendor key with no 429 backoff — F-A20's "never >1 instance" violated by construction. | P2 §4, P4 §5 |
| F-6 | **V-a auth fragmentation.** N `auth.users` per human, no SSO, per-project Auth config (Site URL/redirects/SMTP) as a manual ×N birth step in the same reproducibility class as the dashboard-applied publication gap. | P3 §4, P1 §2 B1b |
| F-7 | **Correlated peak kills V-b's multiplexing story.** All leagues are the same World Cup — kickoff-synchronized load; sharding buys zero temporal spreading, so V-b's shared pool contends at N≈3–5, far below its nominal client ceiling. | P2 §2 |
| F-8 | **Rollback topology.** V-b: one PITR timeline couples all leagues (healthy league rewound by a neighbor's incident). V-a: per-project PITR is a paid add-on ×N. Both inherit F-A15 forward-only ×N. | P1 §4 |
| F-9 | **The dashboard-applied `draft`/`draft_pick` publication gap multiplies.** Known single-DB reproducibility gap (DESIGN_NOTES §7) becomes a manual step at *every* league birth — convert to an idempotent migration before any per-league adoption (also closes BACKLOG OPS-DRAFT-PUB). | P1 §2 B5, P3 §5 |
| F-10 | **Render env groups cannot carry secrets** (`sync:false` forbidden — render.yaml:33-34), so R-2 is N×4 services with per-service hand-entered secrets unless provisioning goes through the Render API (which demotes render.yaml from source-of-truth). | P4 §3 |
