**SUB-DECISION P1-S1 (for the D-DB brief): reference-data strategy under per-league.**
- **Option A — per-league re-ingest:** run the ingest jobs (job:rosters, job:ingest-team-stats, job:ingest-group-standings — apps/worker/package.json:17-19) against each target. Cost: ×N feed calls at birth AND ×N ongoing live-stat ingest every matchday. Under one shared worker looping N DBs, all N ingest streams share the single in-process feed rate limiter (F-A20) — N is bounded by the feed budget; under R-2 worker-per-league, each carries its own limiter but the VENDOR-side budget is still shared. Pro: no new tooling, drift-free by construction.
- **Option B — template clone:** pg_dump the reference tables from a canonical/template DB, restore into the fresh target (V-a: psql into the new project; V-b: `pg_restore --schema`), then ongoing ingest keeps it live (ongoing ×N cost remains — B only saves the birth backfill). Pro: fast birth, no feed calls. Con: new tooling + template staleness window.
- **Option C — shared-reference-DB split (reference in one DB, league data per-league): BREAKS — do not carry forward.** Postgres has no cross-database foreign keys. Concrete casualties: (1) `fifa_match.period_id` itself — the F-C01 FK binds a reference fixture to a league-side `period`; splitting severs the exact edge this fork exists to simplify; (2) the lineup-lock trigger's raw-SQL `JOIN public."fifa_match"` (20260612220000/migration.sql:74-78) cannot join across databases; (3) every Prisma relation traversal (StatPlayerMatch/EventMatch/ShotMatch → FifaMatch FKs with onDelete:Cascade, schema.prisma:730/758/783; lineup/roster → player) — one PrismaClient binds one datasource/database. (A schema-split WITHIN one database, i.e. a V-b sub-shape with a shared `ref` schema, does not have the FK problem — cross-SCHEMA FKs are legal — but inherits all §1 V-b landmines; note for the brief, not developed here.)

## 3. Control-plane vs data-plane

Must live OUTSIDE the league DBs: **(a) the league registry** (leagueKey → DSNs/keys/schema — the routing source of truth; P4 consumes it); **(b) global identity** — variant-dependent: under V-a `auth.users` is per-project, so a person in two leagues is two unlinked auth accounts unless a control-plane IdP/directory is added (the mirror trigger itself needs zero changes — it installs and runs per database); under V-b identity is naturally global but needs the trigger fan-out rewrite (§1 landmine #2); **(c) league-creation authority** (who may birth league #k). NOT control-plane: the allowlist — `allowlist_email` is already leagueId-scoped and seeded per DB (cli.ts:95-103); `push_subscription` is keyed on globally-unique endpoint (F-A08) but is per-DB data-plane (under V-a the same device subscribes per league — acceptable duplication, flag for P3/notify).

**SUB-DECISION P1-S2: registry home.**
- **A — dedicated control DB:** first-class, queryable at runtime (required for R-1 routing); one more DB to migrate/back up; a new SPOF in every request path.
- **B — env/IaC-only (fits R-2):** registry IS render.yaml + per-league env groups; no runtime lookup, no new DB; but nothing can enumerate leagues at runtime (cross-league ops become deploy-time scripts) and secrets stay sync:false-unverifiable (F-A07's audit posture, now ×N).
- **C — league #1's DB doubles as control at N=1:** zero cost today, matches INV-11; must be extracted the day league #2 arrives — a deliberate bridge, not a destination.

## 4. Migration fan-out

Today: `migrate deploy` runs ONCE as the web preDeployCommand (render.yaml:55) against one DIRECT_URL; worker/crons never migrate and there is NO autoDeploy ordering barrier — all 4 services deploy independently on push (AUDIT Lane A3, ~1077-1084). Under per-league:
- **R-2:** each league's web service migrates its own DB on its own deploy. Lockstep exists only if all N deploy together; realistically the fleet is mixed-schema during every rollout window, and N service-sets × no barrier compounds the existing cross-service seam.
- **R-1:** the single preDeployCommand must loop the registry: **control-plane DB first** (if P1-S2=A), then leagues in deterministic (registry) order. Partial failure: league k fails mid-loop → leagues <k on schema v+1, ≥k on v, one code version serving both.
- **Consequence (hard):** code must be N/N+1-schema-compatible in BOTH topologies → the expand/contract discipline that F-A15 (AUDIT:424-429) calls an implicit convention becomes **MANDATORY, permanently** — under per-league there is no deploy where "the" database is atomically at one schema version.
- **Drift detection:** `prisma migrate status` ×N (registry loop; cron-able); wire the existing unwired readiness probe (apps/web/app/api/db-check/route.ts:14-38) per league target so a wrong/empty/stale DB 503s instead of serving.
- **Rollback posture ×N:** F-A15's forward-only, code-only rollback multiplies — a bad migration is now N bad databases. V-a: restore/PITR is per-project (per-project paid add-on — parameterize: `RollbackCost(N) = N × C_PITR`; verify current price at adoption). V-b: one database's PITR restores ALL leagues to the same instant — a healthy league k gets rewound by league j's incident (blast-radius coupling unique to V-b).

**SUB-DECISION P1-S3: migration executor.** **A** — web preDeployCommand loops the registry (R-1; keeps today's single wiring point, render.yaml:55, but a long loop runs inside one deploy's pre-deploy budget and one league's failure semantics must be chosen: abort-all vs skip-and-alert). **B** — dedicated migrate runner (control-plane job that fans out first; app services deploy only after it reports green — introduces the ordering barrier the audit says is missing today, at the cost of a new service + orchestration). **C** — per-league service migrates its own DB (R-2-natural; maximal isolation, zero fleet coordination).

## 5. Teardown (league death)

| Step | V-a | V-b |
|---|---|---|
| Archive | **Pause is NOT available on Pro** — projects on paid plans cannot be paused ([Pausing Pro-Projects troubleshooting doc](https://supabase.com/docs/guides/troubleshooting/pausing-pro-projects-vNL-2a); [discussion #27399](https://github.com/orgs/supabase/discussions/27399)). Reversible soft-delete = transfer the project to a Free-plan org (<500MB DB) then pause, OR pg_dump / Supabase scheduled backups then delete | `pg_dump --schema=league_k` |
| Delete | Delete the project: Postgres + Auth users + Realtime + storage die atomically | `DROP SCHEMA league_k CASCADE` (tables, RLS policies, publication rows, triggers die with it) |
| Key revocation | Automatic and total — the project's anon/service_role keys stop resolving | **None available per-league** — anon/service_role keys are shared across all leagues in the project; a leaked key is a rotate-everyone event |
| Registry/deploy | Remove registry row; R-2: delete the league's Render service set + env group | Same minus keys |

Blast-radius property (stated neutrally, not a recommendation): under V-a a league's death is clean and total — nothing shared with survivors except the org bill; under V-b deletion is scoped but the cluster, keys, Auth, and PITR timeline remain shared. Note the mirror: the same isolation that makes teardown total also makes cross-league surfaces (global standings, shared identity) impossible without a control-plane build.

## 6. N=1 grounding (path from today)

Adoptable while N=1 with ZERO behavior change: (1) write the registry with one row (P1-S2 option B or C costs nothing today); (2) the "provisioning wrapper" is documentation, not code — cli.ts is already fully env-driven (DB URL from env only, cli.ts:5,45) and idempotent, so "birth a league" = point DATABASE_URL/DIRECT_URL at the target, run `migrate deploy`, `provision provision`, ingest, `provision rank`, re-apply the draft/draft_pick publication rows (§2 B5); (3) the 7 `league.findFirst`/`findFirstOrThrow` singleton call sites (8 grep lines incl. one comment; this pass; e.g. cli.ts:61-63) become correct-by-construction under per-league — the one fork where they need no loop-over-leagues rewrite (contrast DESIGN_NOTES §5.4). Client-factory/routing mechanics are P4's lane. The fork's real bill arrives with league #2: project creation + keys, migrate ×2, seed ×2, ingest ×2 under one feed budget (F-A20), publication repair ×2, and the P1-S2/S3 bridges come due.
