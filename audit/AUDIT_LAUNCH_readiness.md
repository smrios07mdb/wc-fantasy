# AUDIT — LAUNCH readiness: public multi-league · UCL retarget · store distribution

**Date:** 2026-07-03 · **Branch:** `audit/launch-readiness` (off `main@2239ed9`) · **Class:** read-only, docs-only
**Mission:** XI ships WC2026 for one private 12-manager league today. Post-2026-07-19 it relaunches as a PUBLIC, MULTI-LEAGUE fantasy app for the UEFA Champions League, distributed natively via the Apple App Store and Google Play (quality bar: best fantasy app in the store). This audit diagnoses readiness and prices the migration. Zero source changes were made.

**UCL format ground truth used throughout:** 36 clubs, ONE league-phase table (Swiss model), 8 matches per club vs 8 different opponents; top 8 straight to R16; seeds 9–24 play a two-legged knockout playoff round; R16→SF two-legged, single-match final. No groups. Club identity (not nations). ~10-month span with multi-week gaps between matchdays.

## 1. Executive verdict

| Gate | Verdict | One-line reason |
|---|---|---|
| **Public web relaunch** (multi-league, open signup) | **NOT READY** | The multi-tenant core does not exist — membership is physically capped at one league per user (`AllowlistEmail.claimedByUserId` global-unique), session→manager resolution has no league dimension, worker crons serve `league.findFirst()` only, and production observability is an unwatched console stream. |
| **Google Play** (TWA/Bubblewrap) | **NOT READY** | The store-side gap is bounded and mostly S/M-effort (assetlinks.json, privacy policy, account deletion, data-safety declarations; the manifest/icon TWA baseline already passes) — but it distributes the web app, so it inherits the public-web NOT READY. |
| **Apple App Store** (wrapped) | **NOT READY** | Magic-link PKCE sign-in cannot complete inside a WKWebView, Web Push does not function in a wrapper (notifications silently dead), and a reviewer's first screen is a marketing page behind an un-passable allowlist wall — the deepest store gap; requires the Capacitor + APNs + auth-bridge thread. |
| **UCL retarget** | **NOT READY** | The tournament model is structurally WC-shaped: national teams in 12 groups (no club/competition-edition concept), exactly 5 single-match knockout rounds hard-rejected otherwise at provisioning, **no aggregate/two-legged-tie concept anywhere**, no team-at-time-of-match snapshot (transfers silently erase history), string-literal period derivation that would leave `period_id` NULL for the entire UCL league phase, and a feed client hardcoded to `/fifa/worldcup/v1`. |

**What already carries over (verified, load-bearing good news):** the scoring engine's stat math is feed-shape-neutral and portable; the guillotine ladder + all-play-all standings arithmetic operate purely on `score_manager_period` and are format-agnostic (a "period" already spans multi-day, multi-match windows); **the RLS policy layer rides multi-tenancy as-is** — every tenant-data SELECT policy is already league-scoped, so the real tenant boundary is app-layer `WHERE leagueId` on the server-bypass path (F-C15); the notify "brain" (trigger selectors, idempotency ledger, preference gate) is transport-agnostic and survives the APNs/FCM swap verbatim; nation-identity rendering is contained behind one Flag surface / one resolver / one kit function; worker tick supervision is genuinely solid (per-tick try/catch, re-entrancy guards, per-item isolation); 30/32 API routes are individually confirmed session-gated.

## 2. Launch blockers in fix order

All 34 blocker=Y findings, sequenced by dependency (schema/identity decisions first; store artifacts parallelizable). Details in §3.

**Tier 0 — decisions that gate everything (no code):** UCL feed provider (INV-1 §6 — nothing can be priced finally without it), membership model (join table vs `manager.user_id`), commissioner model (per-league vs global), wrapper technology (Capacitor recommended), pool semantics for two-legged ties.

**Tier 1 — multi-tenant + competition schema core (migration-class):**
1. **F-C01 / F-C12** — `fifa_match→period` single global FK + unscoped `resolvePeriodId` ("single-league by design"): N leagues cannot bind shared fixtures to their own scoring windows. The deepest schema decision; everything downstream keys on it.
2. **F-D02** — core schema models national teams in 12 WC groups; no club/competition-edition path to a 36-club Swiss table.
3. **F-D03 / F-D04** — knockout model is exactly 5 single-match rounds (provisioning hard-rejects otherwise); no aggregate/two-legged-tie concept in period, lineup-slot, or guillotine-cut models.
4. **F-D01 / F-D07** — no team-at-time-of-match snapshot; a mid-season transfer silently erases a player's pre-transfer stats (current-team gate) and mislabels history.
5. **F-C03 / F-C08** — `AllowlistEmail.claimedByUserId` globally unique: a user physically cannot join a second league.
6. **F-C02** — session→manager resolution has no league dimension (global first-match).
7. **F-C04 / F-C06 / F-C07** — commissioner is a hardcoded global email; stat/rating/penalty corrections write globally per (match,player), a cross-tenant corruption vector.
8. **F-C05** — no invite/join flow at all (admission = operator CLI).
9. **F-C17** — football-reference + GroupStanding assume a single global competition edition.

**Tier 2 — multi-tenant runtime (migration/review):**
10. **F-C09** — draft resolved as a global singleton (`draft.findFirst`, no league clause) across the page loader + six API routes.
11. **F-C10** — pool/dashboard/commish loaders read the whole fixtures table unscoped.
12. **F-C11** — worker recompute/period-close crons process `league.findFirst()` only — one arbitrary league gets serviced at N>1.
13. **F-A06** — standings/playoffs Realtime channels are global; cross-league fan-out (vsfield/draft channels are properly scoped).
14. **F-A08** — push subscriptions keyed per-manager on a globally-unique endpoint: one device ⇒ one league.
15. **F-A07** — Prisma/PgBouncer correctness + connection budget are an unenforced manual runbook step; a capacity cliff at public concurrency.

**Tier 3 — UCL format machine (migration/review, gated on Tier 0 feed decision):**
16. **F-D05 / F-D10** — period-linking derivation is 100% WC string-literals; a UCL feed's league phase and playoff round would silently get `period_id` NULL (no locks, no scoring windows, no ladder).
17. **F-D09** — feed client hardcoded to the WC-only balldontlie surface (`/fifa/worldcup/v1`).
18. **F-D06** — pool engine cannot express a two-legged tie (single-match FT→ET→pens result derivation).
19. **F-D08** — jersey/kit system is a 30-nation flag-color generator; club kits are a rebuild, not an extension.
20. **F-D11** — lock self-heal's "any scheduled team-match in the period" scoping becomes wrong under multi-week UCL periods.
21. **F-D13** — draft is a hard one-per-league lifetime event (`Draft.leagueId @unique`); no season rollover.
22. **F-D12** — "World Cup 2026" branding + "three matchdays" narrative baked into marketing/design copy (also gates the stores).

**Tier 4 — store gate (parallelizable with Tiers 1–3):**
23. **F-B07** — privacy policy / Terms entirely absent (blocks both stores AND public web/GDPR).
24. **F-B08** — no in-app account deletion (Apple 5.1.1(v) + Play requirement).
25. **F-B01** — reviewer-reachability: first screen is a marketing wall + allowlist login no reviewer can pass (certain rejection until a demo path exists).
26. **F-B02** — magic-link PKCE session does not transfer into an iOS webview (auth bridge: in-app OTP `verifyOtp`, ASWebAuthenticationSession, or deep-link hand-off).
27. **F-B03** — no `/.well-known/assetlinks.json` (TWA ships with a browser URL bar without it).

### F-B01 · Wrapped app opens on a marketing website behind an un-passable magic-link/allowlist wall — no reviewer-reachable functionality (Guideline 2.1 demo access + 4.2 repackaged-site)

- **Observed:** The manifest start_url is "/" (site.webmanifest:6). "/" is force-dynamic (page.tsx:35); a logged-out session resolves to the "signin" view and renders MarketingLanding (page.tsx:56-62) — a full scrolling marketing page with in-page #anchor nav (#mechanics/#scoring/#how, MarketingLanding.tsx:227-231) and a © marketing footer (MarketingLanding.tsx:1298-1343). ### F-C01 · fifa_match→period is a single global FK: N leagues cannot bind shared matches to their own periods
**P0** · Launch-blocker: **Y (ucl-retarget, public-web)** · Confidence: verified · Effort: L · Lane C2a · Verification: CONFIRMED
- **Location:** `packages/db/prisma/schema.prisma:391 (+doc 383-402)`
- **Observed:** FifaMatch is global (keyed by balldontlieId) but carries ONE nullable periodId column pointing at a single per-league Period row (:391). The schema doc at :388-390 explicitly states 'ONE private league per tournament, so a single FK holds… A multi-league deployment would instead need a per-league match→period link — explicitly out of scope.' Locking, the recompute dirty-walk, and period-close all read this one column (:384-387).
- **Impact:** With ≥2 leagues sharing a competition, a match can be linked to only one league's period, so the second league's lineup-lock, scoring window, and period-close silently break. This is the load-bearing structural blocker for both same-competition multi-league and any UCL relaunch. Requires a junction table (match_id, league_id, period_id) plus rewiring every consumer that reads fifa_match.periodId.
- **Fix theme:** multi-tenant-period-link

### F-D01 · Mid-season club transfer silently erases a player's pre-transfer tournament stats (current-team gate, not team-of-record)
**P0** · Launch-blocker: **Y (ucl-retarget)** · Confidence: verified · Effort: L · Lane D2 · Verification: CONFIRMED
- **Location:** `apps/web/app/api/player-tournament-stats/loadPlayerTournamentStats.ts:35,39-53; apps/web/src/playerTournamentStats/toTournamentRows.ts:53,55; packages/ingest/src/prismaStore.ts:44-58`
- **Observed:** loadPlayerTournamentStats.ts:44-51 filters completed stat_player_match rows with `OR: [{ homeTeamId: teamId }, { awayTeamId: teamId }]` where `teamId = player.teamId` (line 35), read fresh on every call. The doc comment (lines 39-43) states the invariant this depends on: 'a WC player belongs to exactly one national team and can only appear in that team's matches, so it never hides legitimate data.' packages/ingest/src/prismaStore.ts:57 shows player.teamId is unconditionally overwritten on every roster re-ingest (`...(teamId ? { teamId } : {})`), and ingestRosters runs daily (packages/ingest/src/ingest.ts:76-77).
- **Impact:** In UCL, a club player transferring in the winter window will have player.teamId repointed to the new club by the very next daily roster sync. From that moment, this loader's team-participation filter (keyed on the NEW current teamId) silently excludes every completed match the player played for his OLD club — his pre-transfer goals/assists/points vanish from Tournament Stats with no error, no 'data unavailable' indicator, no partial-season disclosure. toTournamentRows.ts:53,55 independently derives isHome/opponent from the same current-team value, so even loosening the gate would still mis-orient/mis-attribute the opponent for those matches.
- **Fix theme:** identity/history — team-of-record snapshot

### F-D04 · No aggregate/two-legged tie concept exists anywhere — period, lineup-slot, and guillotine-cut models all assume one match decides a round
**P0** · Launch-blocker: **Y (ucl-retarget)** · Confidence: verified · Effort: L · Lane D3 · Verification: CONFIRMED
- **Location:** `packages/db/prisma/schema.prisma:479-504 (LineupSlot @@unique([managerId,periodId,playerId])); packages/commish-core/src/advance.ts:1-20,105-206; packages/recompute/src/periodStatus.ts:60-97`
- **Observed:** A period currently holds many fixtures but exactly ONE lineup slot per player (no leg-scoped identity); repo-wide grep for aggregate/tie/leg concepts returned zero real hits. advance.ts's guillotine cut reads and freezes a single round's score before eliminating.
- **Impact:** Two design paths both break something: modeling a two-legged tie as one period removes a manager's ability to rotate the XI between legs and keeps the period open for the tie's full multi-week span; modeling each leg as its own period breaks the single-round cut/freeze/ordering logic in advance.ts, which has no notion of combining two periods' scores before a cut. Neither path works without a genuine redesign.
- **Fix theme:** two-legged tie scoring/lock model

### F-A01 · No exception/error-tracking service anywhere — every failure is a console line on Render stdout/stderr, so a silent scoring break during a live match is detectable only by a human tailing logs or a user complaint
**P1** · Launch-blocker: **N** · Confidence: verified · Effort: M · Lane A1 · Verification: CONFIRMED
- **Location:** `apps/worker/src/logger.ts:7-13; apps/web/app/api/faab/bid/route.ts:92-97; apps/web/app/api/lineup/route.ts:39-49`
- **Observed:** The worker's only log sink is console.log/console.error emitting single-line JSON (logger.ts:11-12). grep for sentry|datadog|newrelic|opentelemetry|rollbar|bugsnag|logtail across the repo returned hits ONLY in docs/design/prompts — zero runtime instrumentation. Web API routes call their handlers with NO surrounding try/catch and NO logging (e.g. bid/route.ts:95 `await handleSubmitBid(...)`, lineup/route.ts:44); a handler/store throw (DB down, pooler exhausted) becomes an opaque Next.js 500 written only to unstructured stderr, so server 5xx rate is invisible. In the worst live-match case a feed field that is renamed/absent is coerced null->0 by the mapper without throwing (cross-ref p1:F-P1-02), so scores compute as zeros and emit NO log line at all — the only signal is a user noticing wrong points.
- **Impact:** For the current 12 known users this was tolerable. For a public, multi-league relaunch there is no path by which an operator learns the scoring pipeline (or any route) is broken except by actively watching the Render log stream or receiving a complaint. Time-to-detect a live-match scoring failure is unbounded. This is the foundational observability gap the other findings sit on.
- **Fix theme:** Add a shared exception-tracking + structured-log-shipping layer (e.g. Sentry) wired into the worker logger, the web API routes, and server loaders before public launch
- **Cross-refs:** p1:F-P1-02, p0:F-P1-04

### F-A02 · The RESIDENT worker (all live ingestion + recompute) has no dead-man switch — heartbeat/liveness pings exist ONLY for the hourly period-close cron, so a crashed or hung worker during a live match is invisible
**P1** · Launch-blocker: **N** · Confidence: verified · Effort: S · Lane A1 · Verification: CONFIRMED
- **Location:** `apps/worker/src/index.ts:14-64; apps/worker/src/scheduler.ts:50-309; apps/worker/src/jobs/heartbeat.ts:133-158`
- **Observed:** grep for ping(|heartbeat|reportPeriodClose across apps/worker/src shows the heartbeat/dead-man mechanism (heartbeat.ts) is imported and fired ONLY by jobs/periodClose.ts:176,189 (the hourly cron). index.ts and scheduler.ts contain no ping/heartbeat call — the long-running process that runs the ~60s ingestion tick, the live poll, the lock stamping, and runRecomputeSweep (scheduler.ts:218) emits no liveness signal to any external monitor. index.ts:56 handles uncaughtException by exiting; Render will auto-restart a crashed worker but (dashboard fact, unverified) emits no alert, and a HUNG event loop (interval stops firing) is not covered by uncaughtException at all. The period-close cron's heartbeat therefore cannot observe a dead resident worker — it is a separate process.
- **Impact:** The single process responsible for turning live feed data into fantasy scores can die or stall mid-matchday with zero external signal. Combined with finding F-A1-01 (no error tracking), a scoring outage during a live match has unbounded time-to-detect. At multi-league public scale 'watch the logs' is unviable; this is the highest-leverage observability fix.
- **Fix theme:** Emit a per-tick liveness heartbeat from the scheduler to an external dead-man's-switch (Healthchecks.io-style), mirroring the period-close cron pattern already in heartbeat.ts
- **Cross-refs:** p1:F-P1-01

### F-A03 · No metrics/gauges, and normal recompute telemetry is log.debug — SUPPRESSED at the production LOG_LEVEL=info — so a stalled sweep with dirty rows piling up is unobservable
**P1** · Launch-blocker: **N** · Confidence: verified · Effort: M · Lane A1 · Verification: CONFIRMED
- **Location:** `apps/worker/src/scheduler.ts:218-224; apps/worker/src/logger.ts:5-8; render.yaml:39-40; packages/recompute/src/recompute.ts:186-203`
- **Observed:** The full SweepResult (playerMatches, managerPeriods, skippedFrozen, standings counts) is surfaced only via log.debug("scheduler.swept", {...result}) at scheduler.ts:219. logger.ts:8 drops any level below config.logLevel, and render.yaml:39-40 sets LOG_LEVEL=info on the shared env group — so in production scheduler.swept is never printed. The ONLY recompute signal that survives at info is the log.warn at scheduler.ts:222-224 when playerMatchFailures>0. There is no dirty-backlog gauge anywhere (grep for backlog/countDirty in packages/recompute found only the sweep's own listDirty*/claimDirty* consumption). recompute.ts Phase 2 (manager-period, lines 189-197) and Phase 3 (standing, lines 200-202) have no per-iteration onError sink — unlike Phase 1 (168-181) — so a throw there aborts the sweep and collapses to a single generic scheduler.tick.error (scheduler.ts:286) with only a message string, losing which manager/period failed while its dirty markers accumulate silently.
- **Impact:** The classic 'sweep stalled, dirty rows accumulating' failure mode — where scores freeze mid-tournament — produces no metric, no count, and (in prod) not even a normal telemetry line. An operator cannot answer 'is recompute keeping up?' from the logs. No dashboard exists to trend it. This is the metrics-absence the public gate needs closed.
- **Fix theme:** Emit sweep counts + a dirty-backlog depth gauge at info (or to a metrics sink), and give recompute Phase 2/3 the same per-key onError surfacing Phase 1 has
- **Cross-refs:** p1:F-P3-02, p1:F-P2-02

### F-A04 · The in-app detection signals that DO exist (poller-silent, recompute failures, foreign-row skips, malformed-feed skips) are log-only — nothing is wired to any alert channel
**P1** · Launch-blocker: **N** · Confidence: verified · Effort: M · Lane A1 · Verification: CONFIRMED
- **Location:** `apps/worker/src/scheduler.ts:140-142,222-224; packages/ingest/src/ingest.ts:47,203-208,245-249; render.yaml:143-199`
- **Observed:** The codebase has deliberately-built detection heuristics — the poller-silent alert (scheduler.ts:141 log.warn "poller.silent" when a live match has had no successful poll within POLLER_SILENT_GRACE_MS), the recompute failure count (scheduler.ts:223 log.warn), the foreign-match-row guard (ingest.ts:205-207,246-248 console.warn), and the malformed-feed-item skip (ingest.ts:47 console.error) — but every one terminates at a log line. render.yaml wires NO log-based alert or webhook; the ONLY outbound alerting hook in the whole IaC is the period-close cron's PERIOD_CLOSE_HEARTBEAT_URL/ATTENTION_URL (render.yaml:168-171), which are sync:false (operator-set, likely unset — dashboard fact I cannot see) and scoped to that cron only. The group-standings cron (render.yaml:180-199) and the resident worker have no alerting env at all. The poller-silent detector also keys off an in-process Map (scheduler.ts:57 lastLivePoll) that resets on every worker restart, so a crash-loop silently re-arms it.
- **Impact:** Real detection logic was written but its output goes nowhere an operator is pushed to. Whether these warnings are ever seen depends entirely on a human tailing Render logs at the moment of failure. Wiring these existing signals to an alert channel is the cheapest large win for the public gate.
- **Fix theme:** Route poller.silent / recompute.failures / foreign_skipped / malformed-feed events to an alert channel (Render log alert, Sentry event, or webhook); persist poller-silent state so a restart doesn't reset it
- **Cross-refs:** p0:F-P1-04, p1:F-P2-01

### F-A06 · Standings + Playoffs Realtime channels are global/unscoped and will cross-league fan-out under multi-league
**P1** · Launch-blocker: **Y (ucl-retarget)** · Confidence: verified · Effort: M · Lane A4 · Verification: CORRECTED
- **Location:** `apps/web/src/standings/realtime.ts:34,68-76; apps/web/src/playoffs/realtime.ts:35,69-77 (contrast: apps/web/src/vsfield/realtime.ts:63-79, apps/web/src/draft/realtime.ts:69-81 which ARE per-tenant scoped)`
- **Observed:** STANDINGS_CHANNEL = "standings" and PLAYOFFS_CHANNEL = "playoffs" are single fixed channel names (not parameterized by league), and their postgres_changes bindings on score_manager_period/standing/playoff_entry carry NO row filter (`{ event: "*", schema: "public", table: "score_manager_period" }` with no `filter`). The file-header comments explicitly justify this on "ARCHITECTURE §4 pins ONE permanent league" and playoffs/realtime.ts:18-19 even carries a TODO(confirm) acknowledging scoping would be needed otherwise. vsfield/realtime.ts, by contrast, already does it right: `vsFieldChannelName(leagueId)` + `filter: period_id=eq.${periodId}` / `league_id=eq.${leagueId}`.
- **Impact:** Once multiple leagues exist, every client on /standings or /playoffs in EVERY league subscribes to the same two global channels. RLS (verified: standing_select_league_member policy + score_manager_period_select_league_member SECURITY DEFINER helper in packages/db/prisma/migrations/20260606170000_rls_realtime_vsfield/migration.sql:50,72,87) correctly blocks cross-league PAYLOAD leakage, so this is NOT a security/data leak — but every row change from every OTHER league still fires the client's onChange handler, triggering a needless GET /api/standings or GET /api/playoffs refetch (each of which re-runs the full loadStandings/loadPlayoffs Prisma query set).
